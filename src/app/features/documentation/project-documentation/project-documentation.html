GUÍA DE EJECUCIÓN

Desarrollo de la prueba

Esta guía permite preparar la solución completa en un entorno local y conocer la versión disponible en línea.

Prueba en línea

La versión desplegada puede consultarse en http://3.15.151.229/.

La demostración utiliza HTTP y no HTTPS. Al tratarse de una prueba técnica, no se asignó un dominio ni un certificado de seguridad; no debe utilizarse para información sensible o credenciales reales.

Requisitos mínimos

  • Git para clonar los repositorios.
  • Docker Desktop o Docker Engine con Docker Compose v2.
  • Una cuenta de Amazon Web Services con acceso a S3 y un bucket privado para los adjuntos.
  • Node.js 22 o superior con Corepack, únicamente si se desea ejecutar el frontend en modo de desarrollo fuera de Docker.

1. Clonar los repositorios

Crea una carpeta de trabajo y clona los tres repositorios como directorios hermanos. La infraestructura espera encontrar los directorios frontend y backend en el mismo nivel.

mkdir support-ticket-system
cd support-ticket-system
git clone https://github.com/G9Mares/frontend.git frontend
git clone https://github.com/G9Mares/backend_nenis_test.git backend
git clone https://github.com/G9Mares/infraestructura.git infraestructura

Copia los archivos de composición desde el repositorio de infraestructura a la carpeta raíz de trabajo.

cp infraestructura/compose.yaml .
cp infraestructura/compose.dev.yaml .

En Windows PowerShell, sustituye los comandos anteriores por Copy-Item infraestructura\compose.yaml . y Copy-Item infraestructura\compose.dev.yaml ..

2. Configurar Amazon S3

Para probar la carga y visualización de adjuntos localmente es indispensable usar una cuenta de Amazon Web Services. Crea un bucket privado de S3, conserva la región elegida y genera una identidad de acceso con permisos limitados de lectura, carga y eliminación de objetos únicamente sobre ese bucket.

Crea un archivo .env en la carpeta raíz de trabajo. Usa valores propios; nunca subas este archivo ni claves de acceso al repositorio.

MYSQL_DATABASE=support_tickets
MYSQL_USER=support_app
MYSQL_PASSWORD=replace-with-a-local-password
MYSQL_ROOT_PASSWORD=replace-with-a-local-root-password

AWS_REGION=your-aws-region
S3_BUCKET=your-private-s3-bucket
AWS_ACCESS_KEY_ID=your-access-key-id
AWS_SECRET_ACCESS_KEY=your-secret-access-key
JWT_SECRET_KEY=replace-with-a-strong-local-secret
BOOTSTRAP_KEY=replace-with-a-private-bootstrap-key

3. Iniciar la solución

Desde la carpeta raíz, crea las imágenes e inicia frontend, backend y MySQL. Después aplica las migraciones de la base de datos.

docker compose -f compose.yaml -f compose.dev.yaml up --build -d
docker compose exec backend alembic upgrade head

La aplicación estará disponible en http://localhost; la documentación interactiva del backend estará en http://localhost:8000/docs.

4. Crear el administrador inicial

El proyecto requiere crear un usuario administrador mediante una llamada directa al backend. Esta operación solo puede realizarse una vez: cuando ya existe un usuario administrador, el servicio no permite repetirla.

Con la solución completa iniciada mediante Docker, utiliza la ruta expuesta por Nginx. Sustituye todos los valores de ejemplo y usa exactamente la clave configurada en BOOTSTRAP_KEY dentro del archivo .env.

curl --location 'http://localhost/api/auth/bootstrap' \
--header 'Content-Type: application/json' \
--data-raw '{
  "name": "Admin local",
  "email": "admin@example.com",
  "password": "replace-with-a-strong-password",
  "bootstrap_key": "the-value-configured-in-BOOTSTRAP_KEY",
  "phone": "5512345678"
}'

No utilices ni publiques claves de arranque, contraseñas o credenciales reales. Si se invoca el backend directamente mediante el puerto de desarrollo, la misma operación usa http://localhost:8000/auth/bootstrap.

5. Frontend en modo de desarrollo

Si se requiere modificar la interfaz con recarga automática, deja el backend disponible y ejecuta el frontend de forma independiente.

cd frontend
corepack enable
pnpm install
pnpm start -- --host 0.0.0.0

En este modo, la interfaz se sirve en http://localhost:4200 y consume el backend local configurado en el entorno de desarrollo.

METODOLOGÍA

Uso de IA

La IA se utilizó como una capacidad de ejecución dentro de un proceso dirigido y supervisado, no como un sustituto de las decisiones técnicas.

Proceso de trabajo

El desarrollo fue iterativo y se dividió entre agentes especializados desde la definición inicial hasta la implementación de infraestructura, backend y frontend. Esta separación permitió mantener responsabilidades claras, instrucciones específicas y una integración coherente entre las partes.

  1. Definir una necesidad.
  2. Generar instrucciones.
  3. Implementar.
  4. Probar.
  5. Detectar inconsistencias.
  6. Ajustar el contrato.
  7. Volver a probar.
  8. Documentar.

Instrucciones rectoras

Los prompts más importantes fueron documentos de instrucciones detalladas. Definieron responsabilidades, límites, criterios de aceptación y reglas de colaboración para que cada agente actuara con el mismo objetivo.

Instrucciones de implementación del backend backend-implementation-specification.md Instrucciones de implementación del frontend frontend-ai-agent-specification.md

Supervisión y correcciones

Cada resultado generado se revisó antes de integrarse. Cuando se detectaron inconsistencias, se ajustaron los contratos y las instrucciones para volver a validar el flujo. Las propuestas que se salían del alcance, modificaban decisiones aprobadas o no respetaban las reglas del proyecto se corrigieron o descartaron antes de continuar.

Este criterio permitió conservar la rapidez del desarrollo asistido por IA, manteniendo al mismo tiempo control sobre la calidad, la coherencia visual y las decisiones de arquitectura.
